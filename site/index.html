01 — Evidence, not promises

What works today

The tool currently provides hardware and profile diagnostics plus an experimental CUDA 13 launch path with selected native kernels and bounded inference fallbacks.

AVAILABLECLI

GPU inventory and profile checks

Inspect visible NVIDIA devices and compiler tools, review bundled compatibility profiles, and compare a machine’s reported hardware against a target’s published requirements. Unknown facts stay unknown; a profile match is not a workload certification.

Commands: inspect, profiles, audit, and doctor.

Operator-level support

Which PyTorch operations have a path?

These are the current registered paths, with dtype, layout, and size limits. Support applies only to the cases listed; unsupported combinations fail explicitly.

Runs on the GPU

NATIVE sm_52 KERNEL
  • Tensor additionContiguous float32 (up to 1,048,576 values) and int32 tensors (up to 2,147,483,647); same shape/device and alpha=1.
  • Range creationCUDA int64 arange, up to 1,048,576 values.
  • EmbeddingInference with float32 weights and int64 indices; 1D/2D indices and up to 1,048,576 output values.
  • Layer normalizationInference on contiguous float32 input, normalized over the last dimension with float32 weight and bias; up to 1,048,576 values.
  • Matrix multiplicationContiguous 2D float32 matrices; each dimension up to 256 and at most 16,777,216 multiply-accumulate steps.
  • ReLUContiguous float32 tensors, up to 1,048,576 values.

Kernels are compiled by LLVM to PTX for the actual sm_52 device and launched through the CUDA Driver API. These paths do not support autograd.

Runs through CPU fallback

INFERENCE ONLY
  • linear, bmm
  • softmax, scaled_dot_product_attention, GELU
  • add, multiply, divide
  • sum, clamp_min
  • concatenate, contiguous

These use PyTorch’s CPU implementation, then copy results back to the original CUDA device. The dispatcher can also retry eligible out-of-place operations after recognized missing-image, architecture-mismatch, or cuDNN no-engine errors.

Each operation is limited to 64 MiB of CUDA inputs and 64 MiB of outputs. Fallback requires one CUDA device; mutating, alias-returning, and autograd cases fail closed.

The installed CUDA 13 PyTorch wheel provides its own runtime and libraries. This project currently interposes one runtime-version query and does not replace the CUDA 13 API surface or implement general cuDNN, cuBLAS, NCCL, or Triton compatibility.

!

What this means in practice: the launcher is a workload adapter for a narrow PyTorch subset, not a universal CUDA 13 runtime. It currently requires Linux x86_64 and homogeneous visible sm_52 GPUs. Other devices, operations, dtype/layout combinations, training, and library paths need separate implementations and evidence.

02 — Where the gap lives

Compatibility is a stack

A version number can be adapted at one boundary. Useful results require every operation beneath it to have a valid implementation.

01
Application contractPyTorch 2.14 · CUDA 13 wheel

The published PyTorch CUDA 13 profile starts at compute capability 7.5. The adapter’s experimental gate is sm_52; missing kernels and library paths still need real solutions.

TARGET
02
Process interpositionopt-in Python launcher

Prepare a child process with a CUDA Runtime 13.0 version facade and a PyTorch operator adapter. The host driver, system CUDA install, and parent process are not replaced.

BUILT
03
Kernel and fallback routingoperator registry · LLVM / PTX · CPU

Selected supported operations run on Maxwell kernels. A narrow set can fall back to CPU during inference, within explicit size and semantic limits. There is no general binary translator.

PARTIAL
04
Runtime, libraries, hardwaredriver · cuDNN · cuBLAS · device ISA

Every API, library path, dtype, synchronization rule, and instruction must be supported, translated, or replaced. Unsupported proprietary paths cannot be fixed by spoofing a version string.

OPEN WORK
13

Why this project exists

NVIDIA's CUDA 13 release notes say offline compilation and library support for Maxwell, Pascal, and Volta were removed from the toolkit. This project investigates how much useful application behavior can be recovered with a compiler path, adapters, and faithful fallbacks—without hiding the real device.

04 — Try the current prototype

Run it in a controlled environment

Install the package into the same Python environment that already contains the official target PyTorch wheel. The tested launcher setup requires Linux x86_64 and the project’s pinned CUDA 13 PyTorch / LLVM / host-header combination; package installation does not install NVIDIA components.

Install the command where your PyTorch environment can find it

For GPU runs, install CUDA Compatibility into the same active virtual or Conda environment as PyTorch. The command is placed in that environment’s bin/ directory. A user-site install is also available outside a virtual environment; find its scripts path with python3 -m site --user-base and add /bin to PATH. The Python used for that install must already contain PyTorch.

05 — What “full practical support” means

Build coverage from evidence

The project’s destination is machine-wide practical compatibility. Each layer has to earn its support claim through tested behavior.

✓

Truthful discovery

Report actual GPU identity and compute capability; diagnose host prerequisites and target profiles.

IN PLACE
↗

Grow the operator set

Implement or adapt common PyTorch operations with stream, dtype, shape, and error behavior tested.

IN PROGRESS
○

Cover libraries & training

Replace incompatible library paths where needed; validate autograd, optimizers, and training steps.

NOT VERIFIED
○

Qualify cards & workloads

Run representative models and edge cases across each claimed GPU and publish limits, speed, and memory costs.

NOT VERIFIED

A version facade alone cannot supply a missing kernel or reproduce an unsupported instruction. Compatibility means preserving the operation’s behavior or returning an explicit unsupported result.
