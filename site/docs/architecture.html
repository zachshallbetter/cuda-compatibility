How the CUDA compatibility layer works

CUDA Compatibility helps users test selected CUDA 13 PyTorch paths on older NVIDIA GPUs while keeping hardware identity truthful.

The adapter has four boundaries. Each keeps the actual GPU visible and routes only operations with an implementation.

01 · APPLICATIONPyTorch 2.14 CUDA 13Installed wheel and bundled libraries
02 · PROCESS FACADEOne runtime version queryChild process only; reports Runtime 13.0
03 · OPERATOR ROUTERPyTorch dispatcherNative sm_52 path, eligible CPU fallback, or explicit error
04 · EXECUTIONR580 driver + GM200 MaxwellReal device identity and compute capability 5.2

Runtime version facade

The preload interposes only cudaRuntimeGetVersion. With the launcher’s opt-in setting, that call returns CUDA Runtime version integer 13000. Other runtime calls forward to the installed runtime. The CUDA Driver API version, physical device name, compute capability, and installed driver release remain real.

This changes one compatibility check. It does not add CUDA 13 runtime APIs, newer instructions, or missing library kernels. Dynamically linked applications are required for this preload path.

Compiler and native kernels

The launcher invokes LLVM/Clang 23.1.4 to compile packaged CUDA source into PTX targeting sm_52. A small CUDA Driver API bridge loads the module once per CUDA context and launches selected kernels on PyTorch’s current stream. Build outputs are temporary and removed when the child exits.

Native operator registrations cover selected addition, range creation, embedding, layer normalization, matrix multiplication, and ReLU cases. Each has explicit dtype, layout, size, and inference constraints on the support matrix.

CPU fallback and training

For selected operations, PyTorch executes on CPU after a known compatibility failure or a direct fallback registration. Grad-enabled tensors use differentiable framework transfers, and the verified first-order backward path computes the small linear workload on CPU. A separate float32 in-place Maxwell add implements the tested SGD update.

Fallback requires one CUDA device and the 64 MiB input/output limits. Mutating and alias-returning operations fail closed except the bounded float32 add_ route. Training evidence is limited to a 2×2 linear→ReLU→sum model and seven SGD steps on GPUs 1 and 2; arbitrary backward graphs and optimizers remain unverified.

CUDA API and library boundaries

The project bridge directly uses cuCtxGetCurrent, cuModuleLoad, cuModuleGetFunction, cuLaunchKernel, and cuMemcpyDtoH. The launcher interposes only cudaRuntimeGetVersion; other runtime calls are forwarded. On the official CUDA 13 wheel, stock matrix multiplication was observed to fail in cuBLAS initialization with CUBLAS_STATUS_ARCH_MISMATCH, while stock ReLU failed with a missing kernel image. A bounded Titan process-map probe observed CUDA Runtime, cuBLAS/cuBLASLt, NVRTC, cuDNN, NCCL, PyTorch CUDA, and the R580 driver libraries in the wheel/system locations recorded in the research log. A mapped library does not establish that all its APIs are compatible; the project has no complete runtime symbol trace.

What remains outside the layer

  • No system driver, kernel module, CUDA installation, or PyTorch wheel is replaced.
  • No CUDA capability is spoofed; the actual compute capability remains visible.
  • No general binary translator or machine-wide interceptor exists.
  • Proprietary library paths are not broadly reimplemented; cuDNN and cuBLAS failures require operation-specific alternatives.
