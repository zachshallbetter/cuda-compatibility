Support matrix

The current target is useful, bounded PyTorch CUDA 13 execution on Linux x86_64 with homogeneous visible sm_52 GPUs. It is a set of tested paths, not blanket support for the wheel or all CUDA 13 applications.

A

Native GPU implementations

sm_52 kernel

These 19 registered cases cover 37 native operators: addition (in place too), the foreach steps of Adam, AdamW and SGD, subtraction, multiplication and division with broadcasting, range creation, embedding, layer normalization (inference and training), negative log likelihood, copies of strided views, matrix multiplication with and without bias, batched matrix multiplication, ReLU, GELU, softmax, safe softmax and log-softmax, sum over dimensions and fill, with the gradients of each. They run through LLVM-generated PTX targeting the real Maxwell device and the CUDA Driver API bridge; other dtypes and layouts take the CPU fallback below.

No.OperationSupported case
01Tensor additionfloat32 of any size with broadcasting (up to six dimensions), any alpha, or a number; int32 same-shape contiguous tensors up to 2,147,483,647 elements.
02Float16 tensor additionSame-device, same-shape contiguous float16 up to 1,048,576 values, with alpha=1; edge values match exactly.
03Float32 in-place additionA contiguous float32 tensor of any size updated by a broadcast float32 tensor or a number, with any alpha: SGD’s foreach step and gradient accumulation stay on the GPU (#184). Other cases are computed on the CPU and written back.
04Range creationCUDA int64 arange, up to 1,048,576 values. Other cases use the CPU fallback.
05EmbeddingContiguous float32 weight of any size and int64 CUDA indices in 1D or 2D, in training too: the weight gradient (padding_idx included) stays on the GPU. scale_grad_by_freq uses the CPU fallback.
06Layer normalizationInference: contiguous float32 normalized over the trailing dimensions, any size, with or without weight and bias. Training uses PyTorch's decomposition onto row 13.
07Matrix multiplication2D float32 of any size with nonnegative strides, transposed views included, on a tiled kernel; training uses it too (#184). Other dtypes use the CPU fallback.
08Matrix multiplication with biasAs above, with alpha and a bias of any broadcastable shape. Linear layers run through it.
09Batched matrix multiplication3D float32 batches (up to 65,535) of any size with nonnegative strides. Attention runs through it.
10Subtraction, multiplication and divisionfloat32 of any size with broadcasting (up to six dimensions), or a number (1.0 - x included). Other dtypes use the CPU fallback (#184).
11GELUContiguous float32, exact or tanh, and its gradient.
12Softmax and log-softmaxContiguous float32 over the last dimension, masked (-inf) entries included, and their gradients. Safe softmax (attention with a mask) gives zeros for a fully masked row.
13Layer normalization in trainingContiguous float32 over the trailing dimensions, with or without weight and bias, and its gradients.
14Sum over dimensionsfloat32, any dimensions (up to six), keepdim or not.
15FillContiguous float32 tensors (fill_, zero_). Other dtypes are filled in place on the CPU.
16ReLUContiguous float32 tensors up to 1,048,576 values. Other cases, and training, use the CPU fallback.
17Negative log likelihood1D or 2D float32 log-probabilities with int64 CUDA targets: mean, sum or none, ignore_index and class weights, and its gradient. cross_entropy runs through it; a target out of range raises IndexError.
18Copies of strided viewsclone and contiguous of any 1-, 2-, 4- or 8-byte dtype, up to six dimensions: transposes, slices and broadcasts stay on the GPU, and so does the float32 gradient of x[:, i] and unbind.
19Optimizer stepsThe default foreach updates of Adam, AdamW and momentum or weight-decay SGD over contiguous float32 parameters on one device. Other tensors (float16, another device) form their own group, which runs on the CPU; amsgrad, RMSprop and Adagrad’s other steps use the CPU route.

Autograd runs above these kernels: training reaches them through PyTorch’s own backward formulas, and layer_norm, scaled_dot_product_attention and contiguous decompose first. Unsupported backward operators still fail explicitly.

B

Registered CPU fallback operations

Bounded autograd

These 3 registered fallback routes, plus the CPU path that addition takes outside its native limits, use PyTorch’s CPU implementation and copy results back to the original CUDA device:

  • scaled_dot_product_attention (training decomposes it into native matrix multiplication and softmax)
  • clamp_min
  • cat (concatenation)
Limits
  • Training is verified against the CPU, with matching parameters, for small Linear/GELU MLPs with SGD, momentum SGD, Adam and AdamW (their default foreach updates included) and for a Conv2d → BatchNorm2d → MaxPool CNN with momentum SGD, and for nn.LSTM, nn.GRU and nn.RNN (the CUDA-only fused cells run on the CPU, #160). CLC-146-training-workflows-reference-host
  • A sweep of 16 small architectures built from torch.nn (scripts/model_sweep.py) runs inference and two training steps matching the CPU for 14: MLP, ResNet block with BatchNorm, MobileNet-style depthwise convolution with squeeze-excitation, GroupNorm and InstanceNorm CNNs, Conv1d, GPT-style causal decoder, BERT-style encoder with a padding mask, ViT-style patch encoder, a small UNet with transposed convolution and bilinear upsampling, EmbeddingBag, and BCE, Smooth L1, RMSprop and Adagrad. LSTM and GRU fail even at inference (#160). CLC-160-model-sweep-reference-host
  • cuDNN is switched off while the adapter is active: the CUDA 13 wheels' cuDNN has no Maxwell support, so convolution and normalization use PyTorch's own kernels and the CPU fallback.
  • Training through layer_norm, scaled_dot_product_attention and contiguous uses PyTorch's own decomposition, so Transformers, attention and LayerNorm models train, with attention on the math backend; inference keeps the adapter's kernels (#148). A TransformerEncoderLayer matched a CPU copy to 1.5×10⁻⁸ in its first-step gradients.
  • Seven steps measured 2.360 ms median latency on GPU 2 and 7.296 ms on GPU 1, with 67,180,032 bytes peak allocated on each; timing includes CPU fallback and synchronization and is not representative performance.
  • One CUDA device per fallback operation.
  • No single copy between the GPU and host memory moves more than 64 MiB: a larger tensor moves in pieces of that size, each a plain memory copy, with gradients going back the same way. One operation stages at most 1 GiB (set CUDA_COMPAT_FALLBACK_TOTAL_MIB to change it); past that it stops with one plain line. An embedding over 64 MiB copies only the rows it looks up. With these, BERT-base (132M parameters) and GPT-2-small (124M) train one step matching the CPU (#178). CLC-178-fallback-in-pieces-reference-host
  • In-place operators (x += 1, mul_, zero_, fill_, x[i] = v, relu_, nn.ReLU(inplace=True), and the GradScaler steps of torch.amp) run on a CPU copy and are copied back. A strided view such as x[:, 1:3] or x.t() is updated through its contiguous base (#155, #153). Other mutating and alias-returning operators still fail closed. CLC-inplace-fallback-reference-host, CLC-153-155-inplace-general-reference-host
  • Creating a tensor directly on the GPU (torch.zeros, ones, full, rand, randn, eye and similar with device="cuda") builds it on the CPU and copies it over. Random values come from the CPU generator: torch.manual_seed keeps them reproducible, but they differ from a GPU that has kernels. CLC-113-factory-fallback-reference-host

The dispatcher may retry eligible out-of-place operations after recognized missing-image, architecture-mismatch, cuDNN no-engine, or missing CUDA-kernel errors. A fallback is rejected if it cannot preserve the operator’s semantics.

Framework and hardware profiles

TargetPublished package architecture floorProject status
PyTorch 2.14 CUDA 13CUDA 13 package matrix starts at sm_75.Experimental
Selected operators have experimental sm_52 replacements. The official wheel’s other kernels remain unsupported.
PyTorch 2.14 CUDA 12.6Published matrix includes Maxwell starting at sm_50.Comparison only
Useful architecture comparison. It does not prove every operator or library path works.

Three GM200 sm_52 reference cards have run selected baseline operator checks. The float16, strided matrix, cross-stream lifetime, and training cases have been verified on broker-selected GPUs 1 and 2; the library-map probe ran on GPU 2. Candidate cards in the legacy GPU catalog are unverified unless explicitly labeled as reference devices. Compute-capability matches alone are not certification.

General CUDA 13 APIs, arbitrary prebuilt binaries, broad cuDNN, cuBLAS, NCCL, or Triton coverage, arbitrary models or optimizers, recurrent layers such as LSTM and GRU (#160), higher-order gradients (#154), mixed visible architectures, other compute capabilities, performance parity, and machine-wide interposition are not established. Only the training workloads listed in section B have been validated, on broker-selected GPUs 1 and 2. Re-running the two contradicted probes on each new wheel is tracked in #152.

Sources: PyTorch 2.14 release matrix, CUDA 13 release notes, project architecture record.
