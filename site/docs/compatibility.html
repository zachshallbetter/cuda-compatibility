CUDA Compatibility support matrix

CUDA Compatibility helps users test selected CUDA 13 PyTorch paths on older NVIDIA GPUs while keeping hardware identity truthful.

The current target is useful, bounded PyTorch CUDA 13 execution on Linux x86_64 with homogeneous visible sm_52 GPUs. It is a set of tested paths, not blanket support for the wheel or all CUDA 13 applications.

Native GPU implementations

These registered operations run through LLVM-generated PTX targeting the real Maxwell device and the CUDA Driver API bridge.

OperationSupported case
Tensor additionSame-device, same-shape contiguous float32 (up to 1,048,576 values) or int32 (up to 2,147,483,647 elements), with alpha=1.
Float16 tensor additionSame-device, same-shape contiguous float16 up to 1,048,576 values, with alpha=1; edge values match exactly.
Float32 in-place additionSame-shape contiguous float32 CUDA tensors up to 1,048,576 values; scaled updates are used by the verified SGD case.
Range creationCUDA int64 arange, up to 1,048,576 values.
EmbeddingInference only. Contiguous float32 weight, int64 CUDA indices in 1D or 2D, and up to 1,048,576 output values.
Layer normalizationInference only. Contiguous float32 input normalized over the last dimension with contiguous float32 weight and bias; up to 1,048,576 values.
Matrix multiplication2D float32 matrices with nonnegative strides; each dimension at most 256 and at most 16,777,216 multiply-accumulate steps.
ReLUContiguous float32 tensors up to 1,048,576 values.

Native forward kernels do not record autograd formulas. For grad-enabled inputs, eligible operations use the differentiable CPU transfer path; unsupported backward operators still fail explicitly.

Registered CPU fallback operations

These calls use PyTorch’s CPU implementation and copy results back to the original CUDA device:

  • linear and bmm
  • softmax and scaled_dot_product_attention
  • GELU
  • addition, multiplication, and division
  • sum and clamp_min
  • concatenation and contiguous copies

The dispatcher may retry eligible out-of-place operations after recognized missing-image, architecture-mismatch, cuDNN no-engine, or missing CUDA-kernel errors. A fallback is rejected if it cannot preserve the operator’s semantics.

  • First-order gradient and SGD training are experimentally verified only for a small float32 linear→ReLU→sum workload, with foreach=False, on GPUs 1 and 2.
  • Seven steps measured 2.360 ms median latency on GPU 2 and 7.296 ms on GPU 1, with 67,180,032 bytes peak allocated on each; timing includes CPU fallback and synchronization and is not representative performance.
  • One CUDA device per fallback operation.
  • Maximum 64 MiB of CUDA input transfers and 64 MiB of output per operation.
  • Mutating and alias-returning operators fail closed except the registered float32 add_ path.

Framework and hardware profiles

TargetPublished package architecture floorProject status
PyTorch 2.14 CUDA 13CUDA 13 package matrix starts at sm_75.Selected operators have experimental sm_52 replacements. The official wheel’s other kernels remain unsupported.
PyTorch 2.14 CUDA 12.6Published matrix includes Maxwell starting at sm_50.Useful architecture comparison. It does not prove every operator/library path works.

Three GM200 sm_52 reference cards have run selected baseline operator checks. The new float16, strided matrix, cross-stream lifetime, and training cases have been verified on broker-selected GPUs 1 and 2; the library-map probe ran on GPU 2. Candidate cards in the legacy GPU catalog are unverified unless explicitly labeled as reference devices. Compute-capability matches alone are not certification.

Not supported or not verified

General CUDA 13 APIs, arbitrary prebuilt binaries, broad cuDNN/cuBLAS/NCCL/Triton coverage, arbitrary models or optimizers, higher-order gradients, AMP, mixed visible architectures, other compute capabilities, performance parity, and machine-wide interposition are not established. Only the documented first-order training slice has been validated, on broker-selected GPUs 1 and 2.
